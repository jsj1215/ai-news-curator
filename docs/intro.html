WHY

왜 만들었나

백엔드 개발자로서 AI 소식을 따라가려면 여러 사이트를 매일 돌아야 했고, 그중 실무에 쓸 만한 글은 일부였습니다. 고르는 일을 사람 대신 파이프라인이 하도록 만들었습니다.

문제

  • 소스가 흩어져 있음 — Hacker News, Reddit, 국내 기업 기술 블로그를 각각 따로 확인해야 함
  • 신호 대비 잡음이 큼 — "AI" 키워드 글은 많지만 채용 공고, 가벼운 뉴스, 백엔드와 무관한 글이 섞여 있음
  • 제목만으로는 판단이 어려움 — 읽을 가치가 있는지 알려면 결국 본문을 열어 봐야 함
  • LLM으로 전부 평가하면 비용과 쿼터가 문제 — 무료 티어의 분당/일일 호출 한도 안에서 돌아가야 함
→

해결

  • 수집기 3종을 한 파이프라인으로 — Algolia HN API, Reddit RSS, 기술 블로그 RSS 6곳을 2시간마다 수집하고 URL로 중복 제거
  • 규칙 필터를 LLM 앞에 배치 — 키워드, 제외어, 게시 시점, 제목 길이로 먼저 걸러 Gemini 호출 대상을 줄임
  • Gemini가 3개 축으로 채점 — 실용성 40%, 신선도 30%, 깊이 30% 가중 합산 후 상위 3개만 한국어로 요약
  • 쿼터를 코드로 관리 — 5개씩 배치 평가, 호출 간 4초 간격, 일일 800회 상한을 DB 호출 로그로 강제
FEATURES

쌓이는 정보를, 읽을 만한 것만

수집부터 평가, 전달, 모니터링까지. 뉴스 큐레이션의 전 과정을 자동화했습니다.

DESIGN DECISIONS

핵심 설계 결정과 트레이드오프

무료 LLM 쿼터와 외부 소스의 불안정성이라는 두 제약 안에서 내린 판단들입니다.

1LLM 앞에 규칙 기반 필터를 둔다

결정
제목 길이(10자 이상), 게시 48시간 이내, 제외어(채용, hiring 등), AI 또는 백엔드 키워드 매칭으로 먼저 거른 뒤에만 Gemini에 보냄. 키워드 목록은 application.yml로 외부화
이유
수집량 전체를 LLM에 넣으면 호출 수가 수집량에 비례해 늘어남. 값싼 규칙으로 명백한 잡음을 먼저 버림
트레이드오프
부분 문자열 매칭이라 오탐이 있음(예: "ai"가 다른 단어 일부에 걸림). 정밀도는 뒤 단계의 LLM 채점이 보완
RuleBasedFilter.java, FilterConfig.java

25개씩 배치 평가 + 단계적 폴백

결정
기사 5개를 한 프롬프트에 넣어 JSON 배열로 점수를 받음. 파싱 실패 시 개별 평가로, 그것도 실패하면 기본 점수 5.0 부여
이유
호출 수를 기사 수의 1/5로 줄이면서, LLM 응답 하나가 깨져도 파이프라인 전체는 멈추지 않게 함
트레이드오프
배치 응답이 깨지면 오히려 호출이 늘어남. 기본 점수 5.0은 실제 평가가 아니므로 순위가 왜곡될 수 있음
GeminiEvaluator.java

3LLM 응답을 믿지 않는 방어적 파싱

결정
마크다운 코드블록 제거 → 정규식으로 JSON 배열/객체만 추출 → 점수를 0~10으로 clamp → 응답에 빠진 기사는 기본 점수
이유
"JSON만 응답하라"고 해도 모델이 코드블록이나 설명을 붙이는 경우가 있음. temperature도 0.3으로 낮춤
트레이드오프
스키마 강제(structured output) 대신 후처리에 의존하므로 프롬프트가 바뀌면 파서도 같이 점검해야 함
GeminiEvaluator#cleanJsonResponse, GeminiEvaluatorTest

4API 쿼터를 DB 호출 로그로 강제

결정
Gemini 호출마다 api_call_logs에 기록하고, 오늘 호출 수가 800 이상이면 호출하지 않음. 호출 전 4초 대기(분당 약 15회). 요약은 상위 3개에만 수행
이유
무료 티어 한도를 넘기면 이후 호출이 모두 실패함. 재시작해도 카운트가 유지되도록 메모리가 아닌 DB에 기록
트레이드오프
Thread.sleep 방식이라 파이프라인 실행 시간이 호출 수 × 4초만큼 늘어남. 한도 도달 후 남은 기사는 기본 점수로 처리됨
GeminiRestClient.java, ApiCallLog.java

5JVM 락으로 파이프라인 단일 실행 보장

결정
ReentrantLock.tryLock()으로 스케줄 실행과 수동 실행이 겹치면 뒤의 요청은 기다리지 않고 SKIPPED를 반환
이유
동시에 두 번 돌면 같은 기사가 중복 평가·중복 발송되고 쿼터도 두 배로 소모됨
트레이드오프
단일 인스턴스 전제. 여러 인스턴스로 늘리면 ShedLock 같은 분산 락이 필요함
NewsPipeline.java, PipelineControllerTest

6수집기는 인터페이스, 실패는 격리

결정
ArticleCollector 구현체를 List로 주입받아 순회. 수집기 하나가 예외를 내도 로그만 남기고 다음 수집기를 실행. 중복은 URL 유니크 인덱스와 existsByUrl로 제거
이유
RSS 피드 하나가 응답하지 않는 일은 흔함. 새 소스 추가는 구현체 하나와 설정만으로 끝나게 함
트레이드오프
수집기가 순차 실행되어 느린 피드가 전체를 지연시킴. 같은 글이 다른 URL로 올라오면 중복으로 잡지 못함
CollectorOrchestrator.java, CollectorOrchestratorTest

적용

  • 시크릿 외부화 — Gemini 키, 텔레그램 토큰, JWT 시크릿은 환경변수로 주입. 로컬에서는 spring.config.import로 gitignore된 .env를 읽음
  • Stateless JWT — 세션 없이 JwtAuthenticationFilter가 Bearer 토큰을 검증. Access 30분, Refresh 7일
  • BCrypt 비밀번호 해시와 Bean Validation(이메일 형식, 비밀번호 8자 이상)
  • CORS 화이트리스트 — http://localhost:3000만 허용
  • 관리 경로 분리 보호 — /admin/**, /api/pipeline/**, /h2-console은 별도 SecurityFilterChain에서 HTTP Basic + CSRF로 보호. 수동 실행이 Gemini 쿼터를 쓰기 때문
  • API 키를 헤더로 전달 — Gemini 키를 URL 쿼리 대신 x-goog-api-key 헤더로 보내 로그에 남지 않게 함
  • 컨테이너 non-root 실행 — Dockerfile에서 전용 사용자로 전환, H2 콘솔은 prod 프로필에서 비활성화

공개 운영 전 보강할 점

  • HTTPS 필수 — 관리자 인증이 HTTP Basic이라 외부 공개 시 TLS 뒤에 둬야 함
  • 토큰 폐기 없음 — Refresh 토큰을 저장하지 않으므로 만료 전 강제 무효화가 불가
  • 웹 화면과 API의 권한 불일치 — 같은 기사 데이터가 웹 화면에서는 공개, REST API에서는 JWT 필요

GET STARTED

직접 실행해 보기

JDK 17 이상이 필요합니다. Gradle은 래퍼(./gradlew)가 포함되어 있어 따로 설치하지 않아도 됩니다.

1. 환경변수 준비.env는 gitignore 대상

# 템플릿 복사 후 값 채우기
cp .env.example .env

GEMINI_API_KEY=...
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
JWT_SECRET=...  # 32자 이상
ADMIN_PASSWORD=...  # 관리 화면 로그인용

2. 로컬 실행 (H2).env를 Spring이 자동으로 읽음

./gradlew bootRun

# 대시보드
open http://localhost:8080
# 즉시 한 번 실행: 관리자 로그인 후 실행 버튼
open http://localhost:8080/admin/pipeline

3. Docker (PostgreSQL)prod 프로필 + postgres:16

# .env 값을 compose가 주입
docker compose up -d --build

# 헬스 체크
curl localhost:8080/actuator/health

텔레그램 값이 비어 있으면 발송 단계만 건너뛰고 나머지 파이프라인은 동작합니다. Gemini 키가 없으면 모든 기사가 기본 점수 5.0으로 처리됩니다.
